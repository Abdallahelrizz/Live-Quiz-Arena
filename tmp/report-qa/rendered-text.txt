Live Quiz Arena Technical Report
Application Description and Application Layer Protocol
Lebanese American University | CSC430 Computer Networks | Fall 2026
4 November 2026
This report specifies the planned behavior and communication protocol of Live Quiz Arena, a multiplayer
quiz application using direct Python TCP and UDP sockets. It covers technical report sections 1 and 2.
Implementation and experimental evidence will be documented in the later project sections.

1 Application Description
1.1 Purpose and participants
Live Quiz Arena is a real-time quiz application inspired by Kahoot. A host creates a quiz room, shares its
PIN, and manages timed multiple-choice questions. Players join using the PIN and a username and compete
for points awarded by the server. The host manages the game and does not compete. The host application is
a client of the server and may run on a different device.
The shared host screen displays the question and its answer choices. Each answer is paired with a selection
symbol. Player devices show the corresponding symbols, a countdown, answer-acceptance feedback and
the player's cumulative score. They do not receive the active question text or answer text. This makes a
screenshot of the player interface less useful for outside assistance, although it cannot prevent
photographing the shared display. The protocol identifies symbols by position; the final shape or color
artwork does not affect communication.

1.2 Preparing and joining a quiz
The host creates and edits quizzes through the application, saves them as JSON files and loads them for
later use. Each quiz contains between 1 and 100 questions. Each question has 2 to 10 answer choices,
exactly one correct choice, and a host-selected time limit of 1 to 300 seconds. The host loads the quiz
locally and uploads its validated content to the server before starting.
The server issues a unique six-digit room PIN. Players enter that PIN and a username of up to 32
characters; the server rejects invalid PINs and duplicate names within the room. Names are trimmed,
Unicode-normalized and compared without case distinctions. A late joiner starts at zero points and may
answer the current open question using its remaining time. Joining during a pause or between questions
does not start a personal timer.
One server supports independent simultaneous rooms, each with separate players, quiz content, timers and
scores. The required demonstration consists of at least three concurrent rooms with at least five players
each, including a client on a different device over a reachable local network [1]. The per-room start
minimum and maximum capacity remain subject to instructor confirmation; the demonstration target is not
treated as either limit.

1.3 Question flow and scoring
The host starts the first question. The server opens its answer window and controls the deadline. A player
may submit one valid answer per question attempt; once accepted, the answer is final. The client disables
further submissions, while the server independently rejects invalid, duplicate or late requests. Acceptance

feedback reveals neither correctness nor points while answering remains open. The shared screen shows the
live number of answered players.
A question closes when its time expires, every eligible player has answered, or the host closes it manually.
Correctness, earned points and rankings are then revealed. The host explicitly advances to the next
question. After the final question's results, advancing finishes the session and displays the complete final
ranking.
For a correct accepted answer, the score is rounded to the nearest integer, with half-points rounded upward:
                 Points = round half up (500 + 500 × remaining time / question time limit)
Both times use the same unit. A wrong answer or no accepted answer earns zero. For a 20-second question,
correct answers accepted after 5, 10 and 15 seconds earn 875, 750 and 625 points respectively. The server
measures time; a player cannot supply their own timing or score. Paused time does not reduce the speed
bonus.
Players with equal cumulative scores share a single leaderboard row. Distinct scores receive consecutive
ranks: for example, first place may list two names, followed by second and third place. The final
leaderboard includes all participants and their scores, including retained records for players who left or
were removed.

1.4 Host controls and live editing
A manual pause freezes the remaining time and stops answer acceptance while preserving existing
submissions. Resuming continues with that saved duration. Editing the current question first pauses it and
notifies players. Committing the edit clears all submissions for the discarded attempt, creates a new attempt
and restores the full question time. The host explicitly resumes; changing the correct choice is safe because
the discarded attempt earns no points. Cancelling the edit preserves the original question, answers and
frozen time and leaves the quiz paused.
The host may edit, add, delete or reorder future questions during play. The current question's position and
all completed questions are protected. These operations change the future question list without altering the
current timer or accepted answers. Completed content may be edited again after the session finishes, but
historical results remain unchanged. Playing a saved quiz again creates a fresh room with reset scores.

1.5 Connection failures and departures
A network disconnection preserves the player's identity, score and accepted answers. An unanswered
disconnected player remains eligible for the current question, so disconnection does not shorten its timer.
They may reconnect and answer before the deadline; otherwise that question earns zero. A locally stored
random reconnect token restores the session without an account. When host disconnection is detected, an
open question pauses; the host reconnects and explicitly resumes. Detection of a silent failure is not
instantaneous.
A confirmed Leave room action permanently ends that identity's participation. Host removal does the same
and attempts to send a clear removal notice. In both cases the server revokes the existing token, retains
earned points and already-accepted answers, reserves the name, and excludes the departed player from
pending-answer counts. A lost notice does not undo removal. Without accounts, entry under a different new
name cannot be reliably prohibited. Rooms and reconnect state are retained in server memory until server
shutdown; a host who never returns leaves the room paused. Server crash recovery is outside this design.

2 Application Layer Protocol
2.1 Architecture and transport choices
The server is authoritative for membership, phase, timing, answer acceptance and scoring. Clients use one
persistent TCP connection and one UDP socket. The implementation uses Python socket and threading
facilities without HTTP, WebSocket or Socket.IO abstractions [1]. TCP carries commands and
authoritative outcomes; UDP carries replaceable live display snapshots. TCP offers reliable ordered bytes,
but application framing and acceptance replies are still required [2, 4]. UDP can lose, duplicate or reorder
datagrams, so the application handles those properties explicitly [3].

Example configurable ports are TCP 43000 and UDP 43001. Both sockets use IPv4. Every client, including
one on the server machine, uses the same advertised server IPv4 address for TCP and UDP. The server
binds UDP to that address so the source address is predictable. A loopback-only test uses 127.0.0.1 for both
transports. Internet access, NAT traversal and hostile-network security are not assumed.

2.2 Message encoding and boundaries
All messages are UTF-8 JSON objects with v = 1, a type string and a data object. Unknown client fields,
wrong types, duplicate keys, nonfinite numbers and invalid identifiers are rejected. JSON is encoded
compactly without escaping ordinary Unicode text. IDs are UUIDv4 strings except the PIN, reconnect
token and UDP nonce. Durations are integer milliseconds; revisions, sequence numbers and other numeric
fields are nonnegative integers bounded by 2^63 - 1.
A TCP message consists of a four-byte unsigned big-endian length N followed by exactly N JSON bytes.
The length excludes the prefix and must be between 1 and 1,048,576 bytes. The receiver repeatedly reads
until it has the complete header and body. This handles partial reads and multiple messages in the stream
without losing boundaries. Sending uses an ordered writer and sendall. A partial frame has a 10-second
deadline from its first byte. EOF, including EOF in the middle of a frame, ends the connection [4].

2.3 Shared data structures
A Question contains question_id, text, choices, correct_choice_id and time_limit_ms. choices is an ordered
array of {choice_id, text}; question IDs are unique and choice IDs are unique within a question. The host
generates these IDs, while the server validates them. Player question setup contains {question_id,
attempt_id, choices:[{choice_id, symbol_index}], time_limit_ms}; symbol_index is the zero-based choice
position from 0 to 9. The host uses the same ordering with the full text.
A RankRow contains {rank, score, players:[{player_id, username, participation}]}. participation is
ACTIVE, LEFT or REMOVED; disconnection does not change ACTIVE status. A QuestionResult
contains {question_id, attempt_id, correct_choice_id, reason, leaderboard, own_result}. reason is
ALL_ANSWERED, TIMEOUT or HOST_CLOSED. A player's own_result contains {choice_id or null,
correct, points, total_score}; the host's own_result is null. Results refer to frozen closed attempts.
The reusable quiz list is separate from each immutable current/historical attempt. This prevents post-
session edits from changing completed choices or scoring. Technical safety limits are 1,000 characters per
question text, 300 per choice, 100 per title, and 512 KiB for compact quiz JSON. Every quiz mutation and
join is checked against the full 1 MiB outgoing-state budget, including roster, frozen question and result
overhead. These are application limits, not limits imposed by TCP or UDP.

2.5 State snapshots and visibility
STATE data contains control_rev, phase, pause_reason, editing, host_connected, title, question_index,
question_count, current_question, remaining_ms, self, leaderboard, last_result and live. question_index is
zero-based or null before start. phase is LOBBY, OPEN, PAUSED, RESULTS or FINISHED.
pause_reason is null unless PAUSED, when it is MANUAL, EDITING or HOST_DISCONNECTED.
editing is true exactly for an EDITING pause. host_connected is independent, so editing can remain active
while the host is disconnected.
self contains {actor_id, role, username, total_score, submitted_choice_id}; score and choice are null for the
host. A player receives only the symbol-based current_question structure. The host additionally receives
quiz (null before loading, otherwise {title, questions}) and participants:[{player_id, username, connected,
participation, total_score}]. Host current_question also contains the question and choice text. The shared
presentation hides correct-answer/editor metadata. Correct answer IDs never appear in player state before
that attempt closes.
leaderboard contains cumulative scores from completed questions, with zero-score rows initially.
last_result is null or the most recently closed QuestionResult, privately projected for its recipient. live is
always present: null in ordinary STATE or, in active recovery snapshots, {answered_count,
eligible_count}. Each player receives their own serialized snapshot; one player's self or own_result must
never be broadcast to others.
A control_rev or host_connected change sends fresh STATE to every attached ACTIVE client. Joining,
removal and voluntary leave also update all remaining ACTIVE clients. A player-only
disconnect/reconnect updates the host and reconnecting player; it need not notify other players of
connectivity alone. GET_STATE replies only to its requester. STATE is not broadcast for every accepted

answer: that acceptance is private and UDP carries live counts. Clients accept increasing state_rev values
and equal-revision recovery refreshes; older snapshots are ignored.

2.6 Timing and valid transitions
The server measures now_ms = time.monotonic_ns() // 1,000,000. This clock is not affected by wall-clock
adjustments [5]. An OPEN attempt has deadline_ms; remaining_ms = max(0, deadline_ms - now_ms). An
answer is late when now_ms is at or after that deadline. The authoritative acceptance time is sampled after
acquiring the room lock, rather than trusting a client timestamp or first-byte arrival. This policy has
ordinary network and scheduling latency effects; it does not claim perfect latency fairness.
Every serialized handler first closes an overdue OPEN attempt. The timer thread performs the same
deadline check under the same lock, so late timer scheduling cannot admit a late answer. Pause stores
remaining_ms, and resume sets deadline_ms to now_ms plus that saved duration. Accepted submissions
record their remaining time; points are awarded exactly once when the attempt closes. With L =
time_limit_ms and r = accepted remaining milliseconds, the exact half-up score for a correct answer is 500
+ (1000r + L) // (2L). A new answer at r = 0 is rejected.

2.7 Current and future question editing
While OPEN, PAUSED or RESULTS, let k identify the current or just-closed question. Indices 0 through k
are protected; only the suffix after k can be added to, deleted from or reordered. Current-question content
changes use the EDIT_BEGIN and EDIT_COMMIT transaction. ADD_QUESTION inserts before a future
ID or appends when its target is null. DELETE_QUESTION removes a future ID.
REORDER_QUESTIONS supplies every current future ID exactly once, with no omissions or extra IDs. A
newly added question uses an ID never previously used in that room.
The server validates the complete candidate quiz and outgoing size budget before committing a change.
Each successful content/list mutation advances the revisions and reliably refreshes every ACTIVE client's
private STATE. It never changes the current attempt, timer or submissions unless it is EDIT_COMMIT. If
a list change races NEXT_QUESTION, room-lock order and expected_control_rev allow one operation to
succeed; the other synchronizes rather than accidentally modifying a newly current question. Deleting all
future questions makes the current one final; appending before advancement makes the added question
playable.
In LOBBY and FINISHED, the reusable list is fully editable, with 1 to 100 questions. After FINISHED,
question_index, question_count, current_question and recorded results remain the frozen history of that
session even if reusable quiz content changes. A new room is required to replay it. EDIT_CANCEL always
stays paused; no editor action implicitly resumes play.

2.8 UDP registration and recovery
After attaching over TCP, the client sends REQUEST_UDP_BIND. The server returns a new binding_id, a
random 128-bit UDP nonce and server_udp_port. It disables the old binding. The client sends
UDP_HELLO from its receiving UDP socket to that port. The server checks the session, challenge, binding
and TCP-peer source IP, records the observed source port, and confirms with UDP_BOUND over TCP.
The client discards snapshots until that confirmation. Reconnection uses a new session_id and repeats this
binding exchange; the reconnect token never travels over UDP.
Challenges last 10 seconds. HELLO retries are limited to once per second, at most five sends before
renewing over TCP with backoff capped at 30 seconds. A matching HELLO from the same endpoint can be
confirmed again harmlessly; changing the source port needs a fresh binding. Unsolicited or invalid
datagrams receive no response.
The server reads an entire LIVE_STATUS snapshot atomically under the room lock, then sends outside it.
Fields include the room, attachment, binding, question, attempt, control revision, sequence, remaining time
and answered/eligible counts. In PAUSED, time is the stored frozen duration. The client checks server
address/port, current binding, exact room/question/attempt/control revision, and a sequence greater than the
last accepted one. Packets for older or not-yet-confirmed future control states are discarded. A delayed pre-
pause update cannot revive a timer after resuming because control_rev changed.
An isolated lost packet is tolerated: the next complete snapshot supersedes it, and the client estimates the
countdown locally between updates. Duplicate and reordered snapshots fail the sequence test. UDP never
changes phase or determines acceptance. After three seconds without a matching snapshot in
OPEN/PAUSED, mark progress stale and request GET_STATE no more than once per five seconds;
persistent loss triggers rebinding with backoff. No stale polling occurs in LOBBY, RESULTS or
FINISHED. Loss of UDP alone never disconnects a player or pauses the host. The display remains
approximate under delay; the server deadline is authoritative.

2.9 Errors retries and session recovery
Malformed lengths, incomplete frames, invalid UTF-8/JSON, duplicate keys, nonfinite numbers, non-
object payloads and unsupported versions are fatal to that connection. Send a bounded ERROR when safe,
then close; never guess a new frame boundary. Well-formed requests with schema or state errors get a
correlated ERROR and leave the connection usable. Oversized/malformed UDP is silently dropped. An
invalid client must not stop the server or unrelated rooms.

Each logical request has a fresh request_id. After an uncertain connection failure, reconcile fresh STATE
before issuing another action. The server retains each accepted answer's request fingerprint and outcome.
An exact accepted-answer retry returns its historical acceptance and fresh STATE without re-awarding
points or reviving a discarded attempt. A different submission follows normal duplicate rules. For
successful host mutations, retain the last 32 fingerprints and outcomes; a cached retry returns its outcome
plus current STATE. An evicted original command cannot execute again because its expected_control_rev
is stale. Reused cached IDs with different content are rejected. Errors and state/binding/identity recovery
operations are not cached.
One room lock serializes commands, expiry, replay checks, answer insertion, scoring, departures and quiz-
list changes. Identity and connection generation are rechecked inside that lock before executing or
replaying anything. Commit immutable events in order, then write outside the lock through one bounded
writer queue per connection. A slow client is disconnected instead of blocking a room. A 10-request-per-
second attachment limit excludes PONG; recovery does not depend on an unbounded result cache. These
rules support the required threaded implementation; detailed implementation belongs in report section 3.
The server sends PING five seconds after the previous valid PONG, allowing one outstanding ping.
Missing PONG for 15 seconds, EOF, reset or write failure marks disconnection. A client treats 20 seconds
without a complete TCP frame as stalled and attempts reconnect with 1, 2, 4, 8-second backoff capped at
15 seconds. A token consists of 32 cryptographically random bytes encoded URL-safe and is scoped to one
actor and room. The app stores it locally, separately from quiz content.
A valid resume replaces the old TCP attachment and UDP binding, preserving the actor's scores and
submissions. Old queued requests and cleanup callbacks fail generation checks. Replacing an apparently
still-connected host first applies the same pause rule as disconnection, then installs the new attachment;
reconnecting never automatically resumes. Silent failure may consume time before detection, and an
expired attempt is not retroactively paused. Losing the initial create/join response before receiving a token
cannot be securely recovered by username alone.
REMOVE_PLAYER commits REMOVED status and token revocation before attempting a final
REMOVED notice. LEAVE_ROOM commits LEFT status and revocation before its final {left:true} result.
Both preserve accepted answers for normal closing scores and remove eligibility. Notifications use the
ordered writer with a bounded flush and then close; they never interrupt a partially written frame.
Undelivered notification does not restore access. A retained revoked token receives SESSION_REVOKED
with HOST_REMOVED or LEFT_ROOM reason on a fresh reconnect. The app then discards it. No
replacement denial token is issued. A plain connection drop preserves ACTIVE status and reconnect rights.
State and tokens remain in server memory until shutdown. A completed room rejects new joins, while
retained ACTIVE identities may reconnect to inspect final results. Raw sockets do not encrypt this LAN
traffic. The binding challenge and token prevent accidental identity confusion but do not provide protection
against an on-path attacker; stronger identity, Internet security and server-crash recovery are outside this
course design.
